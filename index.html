本课胜利条件

在板上任意挑一个设备，3 分钟内说出它的 DTS 节点、驱动文件、Kconfig 开关和 sysfs 路径。

先建立一张地图

内核不是“一份配置编出一块板”。从源码到板上运行，要经过三层，每层只回答一个问题：

01
板级清单 · SDK 层 回答“构建哪块板”。选择设备树、配置 fragment、U-Boot 与根文件系统。 device/rockchip/.chips/rk3566_rk3568/alientek_rk3568_defconfig
↓ 把选择交给构建系统
02
内核配置 · 代码层 回答“编进哪些代码”。Kconfig 声明规则，.config 记录结果，Makefile 决定编译哪些目标。 kernel/.config → include/generated/autoconf.h → vmlinux
↓ 与 DTB 一起决定运行时
03
硬件描述 · 设备树层 回答“运行哪些设备”。地址、中断、时钟、引脚，以及最重要的：启用还是禁用。 arch/arm64/boot/dts/rockchip/rk3568.dtsi + 板级 .dts → .dtb
↓ compatible 匹配 → 驱动 probe

把这句话记住：内核镜像决定“有哪些代码”，设备树决定“这些代码为谁工作”。 同一份 vmlinux 可以服务外设不同的多块板子，因为板级差异留在 DTS 里，不必改 C 代码。驱动和设备则通过 compatible 这个“合同”相遇。这正是 Linux 一套源码能支撑海量板卡的结构性原因。

跟着 GMAC0 走一遍

① 板级清单只做选择，不描述硬件

# device/rockchip/.chips/rk3566_rk3568/alientek_rk3568_defconfig
RK_KERNEL_DTS_NAME="rk3568-atk-custom"          # :4  用哪份设备树
RK_USE_FIT_IMG=y                                 # :7  打包成 FIT 镜像
RK_KERNEL_CFG_FRAGMENTS="rk3568_atk_net.config"  # :18 叠加哪些配置差异

device/rockchip/.chips/rk3566_rk3568/alientek_rk3568_defconfig

这 20 行里一个 CONFIG_ 都没有。它不描述硬件，只记录“这块板怎么构建”。SDK 的 mk-kernel.sh 会把基础配置、fragment 和 DTS 名一起传给内核构建：

device/rockchip/common/scripts/mk-kernel.sh:63

基础配置由 SDK 的 RK_KERNEL_CFG 提供（device/rockchip/common/configs/Config.in.kernel:5，未覆盖时默认 rockchip_linux_defconfig）。板级 defconfig 的职责，是在这个基线上记录差异。

② fragment 是差异，Kconfig 才是规则

# kernel/arch/arm64/configs/rk3568_atk_net.config
CONFIG_NET_VENDOR_STMICRO=y   # drivers/net/ethernet/stmicro
CONFIG_STMMAC_ETH=y          # 通用 DWMAC 核心
CONFIG_PHYLIB=y              # PHY 抽象层

kernel/arch/arm64/configs/rk3568_atk_net.config

这些不是随手写的开关。每个选项的行为由 Kconfig 声明。看 Rockchip 胶水层的定义：

# drivers/net/ethernet/stmicro/stmmac/Kconfig:150
config DWMAC_ROCKCHIP
        tristate "Rockchip dwmac support"
        default ARCH_ROCKCHIP
        depends on OF && (ARCH_ROCKCHIP || COMPILE_TEST)
        select MFD_SYSCON

kernel/drivers/net/ethernet/stmicro/stmmac/Kconfig:150

三行依赖值得逐个读：default ARCH_ROCKCHIP 让 RK3568 默认打开它；depends on OF 说明没有设备树就没有这个驱动；select MFD_SYSCON 自动带上寄存器访问的依赖。Kconfig 不只是开关面板，它是一张依赖图。

这个选择最终落到四个位置，可以逐级验证：

阶段证据
配置结果kernel/.config:1265 → CONFIG_DWMAC_ROCKCHIP=y
C 代码可见include/generated/autoconf.h:1197 → #define CONFIG_DWMAC_ROCKCHIP 1
编译规则.../stmmac/Makefile:27 → obj-$(CONFIG_DWMAC_ROCKCHIP) += dwmac-rockchip.o
目标文件drivers/net/ethernet/stmicro/stmmac/dwmac-rk.o
注意：磁盘上的 .config 不是运行内核的事实

本仓库里 kernel/.config 的修改时间（10-08）比 autoconf.h、vmlinux（09-21）都新；而且 MFD_RK808 在 .config:2023 是 not set，在 autoconf.h:501 却是 1。磁盘配置与当前镜像不同步。 如果直接拿这份 .config 编译，PMIC 驱动不会进去；而 SDK 脚本通常会用 defconfig + fragment 重新生成配置，结果又可能不同。判断运行内核带什么，永远看板上的 zcat /proc/config.gz；重编前，先确认 .config 是怎么来的。

③ SoC dtsi 给能力，板级 DTS 给策略

/* arch/arm64/boot/dts/rockchip/rk3568.dtsi:2584 */
gmac0: ethernet@fe2a0000 {
        compatible = "rockchip,rk3568-gmac", "snps,dwmac-4.20a";
        reg = <0x0 0xfe2a0000 0x0 0x10000>;
        interrupts = <GIC_SPI 27 IRQ_TYPE_LEVEL_HIGH>, ...;
        status = "disabled";          /* :2610 默认不启用 */
};

kernel/arch/arm64/boot/dts/rockchip/rk3568.dtsi:2584

/* arch/arm64/boot/dts/rockchip/rk3568-atk-custom.dts:442 */
&gmac0 {
        phy-mode = "rgmii";
        clock_in_out = "output";
        snps,reset-gpio = <&gpio2 RK_PD3 GPIO_ACTIVE_LOW>;
        ...
        phy-handle = <&rgmii_phy0>;
        status = "okay";              /* :467 这块板启用它 */
};

kernel/arch/arm64/boot/dts/rockchip/rk3568-atk-custom.dts:442

SoC 的 dtsi 描述“这颗芯片具备什么”，所以 status 默认是 disabled；板级 DTS 用标签 &gmac0 覆盖，只写“这块板接了什么、启用什么”。compatible、reg、interrupts 全部继承，不重复。这是能力与策略分离：一颗 SoC 的 dtsi 服务所有板子，板级文件只记录差异。

顺带记住两个数字：reg 的 0xfe2a0000 会变成 platform 设备名 fe2a0000.ethernet；interrupts 的 27 是 GIC 的 SPI 27 号中断。

④ compatible 是合同，probe 是握手

/* drivers/net/ethernet/stmicro/stmmac/dwmac-rk.c */
static const struct of_device_id rk_gmac_dwmac_match[] = {   /* :2858 */
        ...
        { .compatible = "rockchip,rk3568-gmac", .data = &rk3568_ops },  /* :2896 */
        { }
};

static struct platform_driver rk_gmac_dwmac_driver = {        /* :2914 */
        .probe  = rk_gmac_probe,                              /* :2755 */
        .driver = {
                .name           = "rk_gmac-dwmac",
                .of_match_table = rk_gmac_dwmac_match,
        },
};
module_platform_driver(rk_gmac_dwmac_driver);

kernel/drivers/net/ethernet/stmicro/stmmac/dwmac-rk.c:2858

设备树被加载后，OF 核心把节点变成 platform_device；platform 总线拿设备侧的 compatible 列表，逐项比对驱动侧的 of_match_table；匹配成功后，driver core 调用 probe。这就是“被认领”的全过程。

rk_gmac_probe 先解析 DTS（时钟、复位脚、PHY 模式），上电，然后在 :2798 调用 stmmac_dvr_probe()，把后续工作交给 Synopsys DWMAC 的通用核心（stmmac_main.c）。

设计洞察 · 两层驱动

Rockchip 的 dwmac-rk.c 是 glue 层，只处理这家 SoC 特有的时钟、GRF、电源；Synopsys 的 stmmac 是 core 层，处理通用 MAC 逻辑。compatible 的两个字符串正好对应这两层：rockchip,rk3568-gmac 选 glue，snps,dwmac-4.20a 描述 IP 版本。面试里可以这样说：“BSP 的差异通常在 glue 层，通用逻辑来自上游 core；定位问题先判断该改哪一层。”

迁移练习：换一条总线（课后 5 分钟）

GMAC 在 platform 总线；板上的 RK809 电源管理芯片在 I2C 总线。模型完全一样，只是总线和驱动结构换了名字。先找到它：

# 找到 rk809 的 i2c 设备目录（编号取决于 probe 顺序）
grep -l rk809 /sys/bus/i2c/devices/*/name

# 看它有没有被驱动认领
readlink -f /sys/bus/i2c/devices/<上一步的目录>/driver

# 运行内核到底带不带这个驱动
zcat /proc/config.gz | grep MFD_RK808

然后回答三个问题（先自己答，再展开）：

  1. 设备名为什么是 N-0020，而不是像 GMAC 那样的 MMIO 地址？
  2. 驱动用什么结构注册？匹配表在源码哪一行？
  3. 运行内核的 CONFIG_MFD_RK808 是什么值？和磁盘 .config 一致吗？
对照答案

1. I2C client 由“总线编号 + 7 位地址”命名，0x20 就是 DTS 里的 reg；platform 设备没有自描述总线，所以用 MMIO 地址命名。
2. struct i2c_driver rk808_i2c_driver，见 drivers/mfd/rk808.c:1509；.of_match_table = rk808_of_match，表里含 rockchip,rk809。DTS 节点在板级文件的 :105。
3. 以板上输出为准。如果 /proc/config.gz 是 =y 而磁盘 .config 是 not set，说明磁盘配置不是当前镜像的事实——这正是本课要你养成的区分习惯。
